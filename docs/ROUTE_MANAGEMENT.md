# Admin Route Management — Phase 4 (2026-11-14)

Routes now supports registration, metadata editing, reversible activation,
search, municipality/status filters, pagination, counts and assigned vehicle
inspection. Cards adapt to phone widths. Existing authentication, Jeepney
Management, dashboard and passenger APIs are reused. No operating data is seeded.
Checkpoint: `checkpoint/route-management-2026-11-14`.

## Identity and migration

Migration `007_route_management.sql` was applied successfully locally. It adds
nullable display name, private description, origin/destination terminal names,
boarding notes, private administrative notes, `operations_verified` (false by
default), optimistic version and update timestamp to `registered_routes`.
Existing IDs, assignments, favorites, telemetry and credentials are retained.
Existing metadata update time initially means migration time.

An ordered municipality pair is the canonical service direction: one stored
Boac → Gasan direction does not create Gasan → Boac. The unique database index
rejects duplicate directions, including inactive ones. Reactivate an existing
record rather than duplicating it. A database trigger and strict API schemas
prevent changing ID/origin/destination after creation. To replace a direction,
explicitly register its verified replacement, reassign vehicles through Jeepneys
and deactivate the old route. Favorites remain attached to their original UUID;
they are never silently moved to another direction.

If another database already has duplicate pairs, migration fails transactionally
without deleting/merging anything. Reconcile those records with the owner before
retrying; do not drop the tables. No duplicate issue occurred locally.

## Operational information

The six municipality options are geography, not evidence of service. Register
only owner-verified directions. Optional terminal names (200 characters each) and
boarding information (1,000 characters) can be drafted privately. They enter the
public API only when the administrator explicitly confirms independent verification.
Changing those fields in the form clears confirmation until checked again.
Display name is limited to 120, description to 1,000, administrative notes to
2,000 characters. Text is trimmed and control characters/line breaks rejected.
Blank fields are nullable. No terminal coordinates, map boarding points, roadside
assumptions or terminal-only classifications are generated.

Public `GET /api/routes` retains `{routes,assignments}` and adds nullable
`verifiedOperations: {originTerminal,destinationTerminal,boardingNotes}` to real
route entries. Unverified operations return null. Description and administrative
notes are never included. Flutter parses optional fields, retains them in the
public cache, and displays confirmed information under the selected route while
online. It hides operational claims offline; existing cached/UNKNOWN route and
vehicle behavior is retained. Old responses without these fields remain valid.
Verification is an administrator attestation, not independent system certification.

## Status and assignments

Deactivation requires confirmation and preserves assigned vehicles, favorites
and GPS records. Passenger route selection excludes inactive directions;
favorites stay saved with `available=false`. New assignments are rejected by
the existing Jeepney Management transaction. Existing assignments can be kept
during unrelated vehicle edits. Reactivation restores catalog eligibility without
changing device status or freshness. Offline clients learn changes only after
successful refresh. Dashboard route counts include inactive registered records.

Details retrieve assigned vehicles in pages through the existing vehicle presenter,
including plate, administrative state, GPS freshness and current/historical driver
report distinctions. Freshness ages while open; refresh retrieves newer reports.
“View [identifier]” opens the existing Jeepney Management detail UI, with Back to
Routes navigation. Vehicle editing is not duplicated.

## Protected APIs

All paths below are under `/api/admin`. ADMIN cookie, session expiry/role checks,
exact allowed Origin and `X-AbangQue-Admin: 1` on writes reuse existing middleware.
Writes require JSON and are limited to 60 per administrator per minute. Queries
are parameterized and list totals/rows use a repeatable-read snapshot.

| Method/path | Behavior |
| --- | --- |
| GET `/routes` | `search` (max 120), `municipality=all` or canonical name, `status=all/active/inactive`, `page`, `pageSize` (default 20, max 100) |
| GET `/routes/:id` | Route metadata, version, timestamps, assigned vehicle count |
| POST `/routes` | `origin,destination,active` plus all metadata fields; UUID generated by PostgreSQL |
| PUT `/routes/:id` | Metadata plus `expectedVersion`; identity and active state are rejected here |
| POST `/routes/:id/activation` | `active,expectedVersion` |
| GET `/routes/:id/jeepneys` | Paged assigned vehicles using existing Jeepney Management response |

Metadata JSON fields: `displayName`, `description`, `originTerminal`,
`destinationTerminal`, `boardingNotes`, `administrativeNotes` (string/null),
`operationsVerified` (boolean). List returns `{items,total,counts,page,pageSize}`;
counts include all stored directions while total matches filters.

Strict schemas reject mass assignment. Invalid input returns 400, denied requests
401/403, missing routes 404, duplicate direction/version conflict 409, throttling
429 and sanitized database failure 503. Row locks and expected versions serialize
updates. Duplicate in-flight UI saves are blocked. Recoverable failures retain
input; uncertain write outcomes instruct the admin to check the saved record
before retrying. Expired sessions use the existing sign-in flow.

## Browser and passenger acceptance steps

1. Open Routes, check counts and empty/filter states at desktop and phone widths.
2. Add an actual verified direction. Leave optional fields empty if unknown.
   Same endpoints and duplicates must fail; no reverse service should appear.
3. Edit metadata. Direction controls remain locked. Change terminal information,
   verify that confirmation clears, and explicitly reconfirm only if verified.
4. Assign a vehicle through Jeepneys. Open Route Details and its assigned vehicle.
5. Save this route as a signed-in passenger favorite. Deactivate with confirmation,
   refresh the passenger app, and check that the direction disappears and the
   favorite is unavailable. Reactivate and refresh; no stale report becomes fresh.
6. Compare public data without credentials:

```powershell
(Invoke-RestMethod http://127.0.0.1:3000/api/routes).data
(Invoke-RestMethod http://127.0.0.1:3000/api/jeepneys).data
```

7. Verified operational fields should appear only when confirmed. Disconnect and
   refresh the passenger app: cached route availability remains unverified and
   operational confirmation text is hidden. Reconnect and refresh to recover.
8. Open two admin edits: after one saves, the other must report a version conflict.
   Stop the API and check retry/error presentation without false success.

These are owner acceptance instructions, not claims of manual browser/phone tests.
Physical-device and browser visual acceptance were not performed in this phase.
